## 2. 本次目标

- **为什么改**：多来源串行导致冷启动过慢（实测 115s/12 请求）；单 provider 超时会拖慢整个任务（一次 Crossref 超时占 30s）；429/timeout 难定位；只有 stage 名、没有阶段耗时；用户无法理解"为什么慢"。
- **解决什么**：① provider 级并发；② 超时策略；③ **阶段耗时打点**；④ 错误语义细化；⑤ 前端轻量性能反馈；⑥ 第二档筛选与 `ccf_rank=none`。
- **不解决什么**：不新增搜索算法/评分体系/AI Agent/PDF RAG/投稿推荐/社交/大量动画/新图形库。
- **禁止改变的语义**（本版本约束）：检索来源业务逻辑、身份归一化、lexical/semantic 评分公式与权重、`score_context_id`、CCF 分类与目录、导出格式、MCP schema、用户项目数据结构（除非向后兼容迁移）。

## 4. 修改记录

### M1（P0#4）阶段耗时打点

```text
问题：检索任务只有 stage 名，没有准确阶段耗时；用户与开发者都无法回答"这次为什么慢"。

根因：任务链路（api.operation → workflow.systematic_search → SourceManager.search_all_sources_result
      → 排序/落盘）中没有任何计时；http_budget 只统计请求数，不统计时间。

修改：
  1) 新增 litsearch/timing.py：StageTimer（线程安全、累加、忽略非法值、**任何情况下不抛异常**），
     阶段常量与 provider 子表；timed_call 辅助。
  2) sources.py：provider 循环内对每个 provider 单独计时，写入 self.last_provider_timings。
  3) search.py：systematic_search 内计时 query_planning / provider_total / normalization /
     ranking / total，合并 provider 耗时，写入 state.search_manifest["timings"]；
     在检索前与检索后（finally，含异常路径）各落一次快照，保证 partial/failed 任务也有耗时。
  4) api.py：翻译阶段（prepare_query）计时，搜索结束后并入 manifest 的 timings。
  5) jobs.py：_timings(state) 把 manifest 里的 timings 复制进 job payload（成功与失败路径都写）；
     读取失败返回 {}，绝不影响任务结果。
  6) tests/test_timing.py：8 项回归。

涉及文件：
  litsearch/timing.py（新增）
  litsearch/sources.py、litsearch/search.py、litsearch/web/api.py、litsearch/web/jobs.py
  tests/test_timing.py（新增）

验证方法：
  pytest -q tests/test_timing.py tests/test_audit_hardening.py tests/test_v093_pipeline.py \
            tests/test_web_api.py tests/test_web_persistence.py tests/test_provider_cooldown.py
  → 111 passed

结果：
  - search_manifest["timings"] 含 query_planning / provider_total / providers{...} / normalization /
    ranking / total，数值非负、JSON 可序列化；
  - 失败路径（检索抛错）仍带 query_planning 与 provider_total（实测 {'query_planning': 0.0035, ...}）；
  - job payload 新增 timings 字段（向后兼容：新增键，不改既有键语义）。

风险：
  - manifest 新增键会让 search_manifest 变大（量级：<10 个浮点数），可忽略；
  - 计时口径随并发改造变化：M2 之后 provider_total ≈ max(providers) 而非 Σ（见 M2 对比表）；
  - 尚未与 http_budget 做"时间-请求"联合分析（P1 待办）。
```

### M2（P0#2）provider 级受控并发

```text
问题：多来源串行抓取。冷启动实测 115s / 12 次请求（平均 9.6s/请求）；一个慢来源
      （Crossref 单次超时约 30s）会把其它来源的结果一起推迟。

根因：SourceManager.search_all_sources_result 用单个 for 循环逐个调用
      source._search_papers_result，全程无线程/异步，各 provider 的等待时间被简单相加。

修改（最小侵入，不重写 provider）：
  1) 保留每个 provider 自身的 pacing 与 429 冷却（provider-local、per-instance），只把
     "同时进行几个 provider"改为受控并发：ThreadPoolExecutor(max_workers=workers)。
  2) workers = min(provider_concurrency(), provider 数)；provider_concurrency() 读
     LEEXTRACTOR_PROVIDER_CONCURRENCY，默认 5，硬上限 16，非法值回退默认并告警。
  3) 先提交全部任务，再按 provider 计划顺序 future.result()：下游读到的顺序与串行一致。
  4) 异常语义不变：每个 provider 的异常仍经 retrieval_status_for_exception 转为
     canceled / timeout / budget_exhausted / rate_limited / provider_error，不影响其它 provider。
  5) 并发 ≤1 或只有 1 个来源时走原串行路径（与 v0.9.11 行为完全一致，便于灰度与回退）。
  6) 共享状态审计：HttpBudget 自带锁、_PROVIDER_COOLDOWNS 有 _COOLDOWN_LOCK、每个 provider 独立 session；
     唯一薄弱点按源 HTTP 缓存（sqlite）→ cache.py 的 6 处 connect 增加 timeout=15 忙等待。

涉及文件：
  litsearch/sources.py（受控并发 + provider_concurrency()）
  litsearch/cache.py（sqlite busy timeout）
  tests/test_provider_concurrency.py（新增 10 项）

验证方法：
  ① pytest tests/test_provider_concurrency.py：重叠、上限、单点失败不丢结果、429 隔离、
     取消仍有效、顺序保持、provider 计时、串行路径、空查询短路
  ② 真机受控 A/B：同一查询、同一 5 个来源、各自冷缓存，唯一变量 = LEEXTRACTOR_PROVIDER_CONCURRENCY

结果（真机 A/B，2026-10-12）：

| 指标 | Before（并发=1） | After（并发=5） | 变化 |
|---|---:|---:|---:|
| provider_total | 10.68s | **3.73s** | **−65%** |
| Σ(各 provider) | 10.68s | 11.82s | 基本不变（工作量未变） |
| 墙钟总耗时 | 15.6s | **8.3s** | **−47%** |
| ranking | 0.36s | 0.29s | ≈ |
| 结果 / 状态 | 30 条 / partial | 30 条 / partial | 一致 |

  形状证据：provider_total 由「求和」变为「取最大」（3.73s ≈ 最慢来源 openreview 3.72s），
  而 Σ(providers) 未下降 —— 省下的是串行等待，不是少做的事。

风险：
  - 并发下共享缓存/预算的争用需在 soak 中观察（v0.9.14 §2 条目 5/6/7）；
  - 多个来源会同时占用上游配额，"429 同时到达"概率上升；冷却仍是 provider-local，总请求数由 HTTP 预算把关；
  - 结果顺序靠"按计划顺序取回"保证；将来若改为 as_completed，必须同步更新下游假设。
```

### M3（P0#3）超时策略：connect/read 分离且可配置

```text
问题：单请求统一 timeout=30（9 处）与 timeout=20（1 处）；一次主机无响应即可阻塞检索 30 秒
      （冷启动 115s 中，一次 Crossref 超时独占约 30s）。

根因：所有 provider 适配器把超时写死在同一个数值上，既未区分 connect 与 read，
      也无法按部署环境调整。

修改：
  1) 新增 DEFAULT_CONNECT_TIMEOUT = 5.0、DEFAULT_READ_TIMEOUT = 12.0 与 http_timeouts() → (connect, read)，
     可用 LEEXTRACTOR_HTTP_CONNECT_TIMEOUT / LEEXTRACTOR_HTTP_READ_TIMEOUT 覆盖；
     非法值或 ≤0 回退默认并告警。
  2) sources.py 中 10 处写死的 30/20 秒全部改走 http_timeouts()（含一处遗漏的内联 timeout=30）。
  3) provider 级外层 deadline（TOTAL_TIMEOUT_SECONDS）保持不变，仍是"单来源总时长"的唯一上限；
     重试策略不变（429 立即返回并进入冷却、5xx 重试、其它 4xx 为最终答案、取消/超时/预算异常不重试）。

涉及文件：litsearch/sources.py、tests/test_http_timeouts.py（新增 5 项）

验证方法：
  pytest tests/test_http_timeouts.py —— 默认值、可配置、非法值回退、
  "不再存在写死的 timeout=30/20"护栏、读超时映射 TIMEOUT 状态

结果：单请求上限由 30s → connect 5s / read 12s。真实网络下的端到端收益需在 v0.9.14 故障注入中量化，
      本条目不宣称具体数字。

风险：
  - 对"慢但正常"的接口（大分页批量）12s read 可能偏紧 → 已提供环境变量覆盖并保留 provider deadline；
    若出现真实回归，优先调 LEEXTRACTOR_HTTP_READ_TIMEOUT 而不是改代码；
  - 收紧超时会略微提高 timeout 状态占比（可观测、可解释，不是数据丢失）。
```

### M4（§5）错误语义细化：auth_error 与 cached

```text
问题：401/403 与 400/422 一起被归入 "contract"，最终都显示成通用的来源错误；
      "答案来自缓存" 与 "答案来自实时请求" 在上层无法区分。

根因：diagnostics._CLIENT_ERRORS 把 401/403 与参数类错误混在一个桶里；
      RetrievalResult 只报告请求数，没有暴露"本次零实时请求但命中缓存"这一事实。

修改：
  1) diagnostics：新增 SourceErrorKind.AUTH 与 AuthError；classify_http_error 把 401/403
     单独归类（仍然不可重试，"是否可重试"的判定不变）。
  2) retrieval：新增 RetrievalStatus.AUTH_ERROR（映射 StopReason.API_FAILURE）与
      RetrievalResult.cached 派生属性（cache_hits>0 且 requests==0），并写入 to_dict()。
  3) sources.retrieval_status_for_exception：SourceError(AUTH) → AUTH_ERROR。
  说明：cached 刻意做成"成功的修饰位"而不是新状态——缓存命中是成功，不是失败模式，
      避免调用方把它当成异常分支。未新增除 auth_error 之外的枚举（遵守"不过度增加枚举"）。

涉及文件：litsearch/diagnostics.py、litsearch/retrieval.py、litsearch/sources.py、
          tests/test_v0912_semantics.py（新增 7 项）、tests/test_offline.py（按新语义更新 1 处断言）

验证：pytest tests/test_v0912_semantics.py（401/403→auth_error、400→contract、404→not_found、
      429→rate_limited、cached 语义、AUTH_ERROR 不可用判定）
结果：鉴权失败可被单独识别并给出"检查 API Key"的提示；缓存命中可观测。
风险：新增一个状态值，消费方若硬编码状态白名单需同步（仓库内已全部走 ok/failed/genuine_empty 判定）。
```

```text

涉及文件：web/src/App.vue、web/src/styles.css、web/src/App.dom.test.js（新增 2 项 DOM 用例）

验证：npm run test（15 passed，含"摘要一行 + 诊断折叠"用例）

同一块信息一半持久一半临时，体验不一致。已改为从 `search_manifest.timings.total` 渲染持久摘要行
（"上次检索 · 30.0s · 6 个来源 · 3 成功 · 1 受限 · 2 失败"），任务面板保留实时阶段与折叠诊断。
真机验证（UI 触发的一次检索）：`total 30.02s`，其中 `provider_total 7.38s`（Σ 各来源 14.87s → 并发生效）、
`ranking 22.61s`（100 条冷向量）、`embedding_load 3.50s`、`translation 1.44s`。

**过程事故记录（同一类问题第二次发生，必须记）**：清理旧构建产物时我的正则写成
`index-[A-Za-z0-9_]+\.(js|css)`，**漏掉了带连字符的 hash**（`index-Dn6Qb-gu.js`），
于是"未引用"判定把**新 JS 当成旧产物删掉**，页面白屏风险。
修正：正则改为 `index-[A-Za-z0-9_-]+\.(js|css)`，并在删除前后都打印引用清单与实际文件清单做交叉校验
（已验证 dist 与 litsearch/web/static 两侧一致、index.html 引用完整）。教训：**任何"按引用清理"的脚本，
匹配模式必须覆盖真实文件名全集，且删除前先打印将要删除的清单。**
```

### B1（§10）Benchmark 实测

环境：Windows 11 / Python 3.12 / 5 个无密钥来源（S2、OpenAlex、arXiv、Crossref、OpenReview）；
驱动方式：`_ui_audit/bench_v0912.mjs` 只经 HTTP 调用真实服务；原始数据
`_ui_audit/bench-out/v0.9.12.json`。故障注入为**配置级**：read timeout 设 1ms 的实例等于强制所有来源超时。

| 场景 | wall p50 | provider_total p50 | ranking p50 | 请求 p50 | 重试 | 限流 | 记录 p50 | 状态 | 最慢来源 |
|---|---:|---:|---:|---:|---:|---:|---:|---|---|
| 暖缓存 · semantic | 0.6s | 0.04s | 0.26s | 0 | 0 | 1 | 30 | partial ×3 | openreview 0.03s |
| 暖缓存 · lexical | 0.6s | 0.04s | 0.14s | 0 | 0 | 0 | 30 | partial ×3 | openreview 0.02s |
| **冷缓存 · semantic** | **15.5s** | **4.31s** | **10.83s** | 5 | 0 | 0 | 30 | partial ×3 | openreview 4.30s |
| **故障注入 · 全部来源超时** | **8.7s** | **8.62s** | 0.00s | 9 | 8 | 0 | 0 | partial ×2 | openalex 8.61s |

provider 延迟 P50（全部样本）：openreview 0.04s、arxiv 0.02s、openalex 0.02s、crossref 0.01s、semantic_scholar 0.01s。

**读法与两个真发现**：

1. **冷启动的瓶颈已经转移**：并发把来源阶段压到 4.31s，但 `ranking` 变成 10.83s —— 这是冷向量缓存下
   对 30 条摘要做本地 MiniLM 编码的净计算时间（暖缓存同一操作 0.26s）。也就是说 v0.9.12 之后要再快，
   必须动排序（两级排序：先词法取 top-N 再编码），而不是继续压来源。
2. **故障隔离可量化**：5 个来源全部超时时，`provider_total` 仍是 8.62s（≈单个来源的最坏耗时），
   串行实现下会是 ~43s；且请求数 9 / 重试 8 都被记录，状态全部为 `timeout` 而非崩溃或静默 0 篇。

**对比 v0.9.11（Before）**：冷启动 115s / 12 请求（平均 9.6s/请求，一次 Crossref 超时独占 30s）→
本版本冷启动 p50 **15.5s**；并发 A/B 的受控对比见 M2。注：两次冷测的查询与上游限流状态不同，
不作为严格同条件对比；同条件对比以 M2 的 A/B 为准。

### M7（UI，参照原型）纵向动画菜单 + 首页字标动画 + 抽屉退场动画

