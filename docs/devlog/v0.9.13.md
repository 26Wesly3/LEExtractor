## 4. 本版修复的真实缺陷

**P0 · 反向代理后 API 一律 403**
- 现象：`app.py` 中间件只接受 `Host ∈ {127.0.0.1, localhost, ::1}`，容器/反代场景 Host 是 DuckDNS 域名。
- 根因：单机安全默认值被硬编码，没有配置出口。
- 修法：新增 `LEEXTRACTOR_PUBLIC_HOSTS`（逗号分隔），默认空 → 行为与之前完全一致（`tests/test_web_api.py::test_host_guard` 仍断言 `Host: evil.example` → 403）。
- Before：公网必 403 / After：显式配置后可达，未配置仍本机独占。

**P1 · 并发上限名存实亡**
- 现象：`ADR-003` 写了 `LEEXTRACTOR_MAX_ACTIVE_SEARCH_JOBS`，代码里没有；实际靠全局锁串行。
- 修法：实现为**进程级**信号量（默认 1）。这里踩过一次坑：我最初写成"每个 JobManager 一个信号量"，被既有测试 `test_web_contract_review.py::test_global_http_lock_keeps_projects_separate_and_queued_cancel_never_execute` 当场抓住（"another app bypassed the global retrieval lock"）——两个 app 对象会各自放行，等于并发翻倍。已改回进程级共享信号量，该测试恢复通过。

### 10.2 P0 缺陷：反代后同源校验把浏览器请求全判 403（前端白板）

- **现象**：公网打开页面是**白板**。首页 HTML 200、JS 659 KB 200、CSS 398 KB 200 —— 静态资源全正常。
- **定位**：带浏览器 `Origin` 的请求全 403：

```
GET  /api/projects  无 Origin            -> 200
GET  /api/projects  带 Origin(https)     -> 403 origin_rejected
POST /api/projects  带 Origin(https)     -> 403
```

- **根因**：中间件比较 `parsed.scheme != request.url.scheme`。Caddy 终止 TLS 后，应用看到的 scheme 是
  **http**，而浏览器发的 `Origin` 是 **https** → 判定不同源 → 全部 403 → 前端拿不到数据 → 白板。
  与 §4 的 Host 守卫是同一类"单机安全默认值没有考虑反向代理"的缺陷。
- **修法**：有效 scheme 取 `X-Forwarded-Proto`（Caddy 已设置），回退到 `request.url.scheme`。
  信任该头是安全的：应用只监听 `127.0.0.1:8012`，除反向代理外无人能到达它伪造该头。
- **回归测试**：`tests/test_deployment_v0913.py::test_reverse_proxy_origin_is_accepted_but_other_origins_are_not`
  —— 覆盖"代理带 https Origin → 200"、"外来 Origin → 403"、"伪造 http scheme → 403"。
  （第一版断言我自己写错了：把"无代理头时的 https Origin"写成应当 200，实际它必须 403 —— 已改正。）
- **修复后公网实测**（`https://leextractor.duckdns.org`，带 Origin）：
  `/api/projects` 200、`POST /api/projects` **201**、`POST /api/demo/projects` **201**、
  `/api/health` 与 `/api/health/ready` 200、`/api/openapi.json` 200。

> 这是本版第 3 个"只有真跑部署才会暴露"的缺陷（前两个：compose 构建上下文、镜像缺 `[web]` extra；
> 加上更早的绑定地址/数据目录默认值）。**四条都不是读代码能看出来的。**
